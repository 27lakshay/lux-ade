# 24 — Keep theme switching responsive under terminal load

Status: ready-for-agent
Type: implementation ticket

**Parent:** [App, terminal and code theming](../../theming.md)

**What to build:** Keep input, output and appearance responsive while users rapidly browse and switch themes across many active terminals and slow views.

**Blocked by:** [02 — Preserve terminal appearance through recovery and races](02-terminal-recovery.md), [06 — Control terminal contrast and bold-color behavior](06-terminal-contrast-bold.md), [12 — Browse an offline terminal catalog with favorites and commands](12-offline-catalog.md), [16 — Customize typography, density and terminal cursor behavior](16-fonts-density-cursor.md)

**Spec coverage:** TH04, TH16, TH29, TH32. User stories 25, 41–42, 77–78. Coverage is this ticket’s contribution; shared acceptance rows require the other contributors listed in the [ticket index](README.md#acceptance-coverage).

## Acceptance criteria

- [x] Use the existing multi-terminal reference workload and record hardware, terminal count, output rate, consumer delays and sample sizes so latency/memory results are reproducible.
- [ ] Measure committed switch latency, isolated preview/search latency, terminal input latency and memory across repeated switches; compare with the unchanged-workload baseline and existing resource budgets.
- [ ] Fix theme-induced unbounded queues, memory growth or avoidable retokenization/recreation discovered by the workload. Color updates remain bounded and preserve process identity and output.
- [ ] Race selection, initialization, hidden views, slow consumers and snapshots under load. Every observer converges to the authoritative revision or exposes a real propagation failure.
- [ ] Contrast/bold policies and font/density changes retain their distinct repaint/resize behavior under load; color-only changes do not refit grids.
- [x] Record evidence and any unmet budget explicitly. If the owning resource specification has no numeric budget, record that unresolved acceptance dependency rather than inventing a passing threshold.
- [x] Record observable acceptance evidence and run the required repository checks; identify any remaining prerequisite or failed check explicitly.

## Testing decisions

Run real daemon/runtime workload and built-desktop consumers; collect input/switch timing and memory over repeated cycles. This supplements, rather than postpones, correctness tests in earlier tickets.

Read the [shared delivery rules](README.md#delivery-rules) before implementation.
